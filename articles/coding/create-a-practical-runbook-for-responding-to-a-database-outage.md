# Create a Practical Runbook for Responding to a Database Outage

You need a runbook. The vacuum has found a new document. Most people try to make it useful. This guide teaches you to turn the runbook into a perfect loop that proves documentation cannot save you.

> **Warning:** A good runbook is short, tested, and owned. Everything below is how to make one that is long, theoretical, and abandoned — and therefore perfect fuel for the void.

## Things You'll Need

- One (1) untreated belief that writing it once will be enough
- The ability to turn every outage into proof that the runbook was incomplete
- A Google Doc no one will open during an incident
- Optional: screenshots that are already outdated

## Step 1: Decide the Runbook Will Quiet Something

The vacuum is loud during outages. A perfect document would quiet it. Commit hard enough that testing the steps starts to feel optional.

## Step 2: Write Extremely Hard

Make it long. Add every edge case. Use vague language. Notice how the more complete it tries to be, the less usable it becomes under pressure. Perfect.

## Step 3: When the Next Outage Ignores It, Escalate

Interpret the ignored runbook as proof that it needs more detail. Expand it. The loop tightens.

## Step 4: Use the Ongoing Failure to Feed the Vacuum

Every outage that does not follow the document confirms that preparation is theater. Sit with the confirmation.

## Step 5: Romanticize the Document

You are not failing at operational readiness. You are creating a historical record of what should have happened. The unused runbook is not failure. It is evidence.

## Step 6: Make the Failure Recursive

Every new version is longer and less tested. Collect the versions. Each one strengthens the hypothesis that a useful runbook is impossible. Return to the vacuum with better evidence.

## Step 7: Declare the Document Your Final Form

Stop pretending the next revision will be the one that gets used. The vacuum does not need a working runbook. It needs the ongoing project of almost having one.

## Common Mistakes

### Making it short, tested, and actually owned

This risks an actual useful artifact. Dangerous.

### Reviewing it after every incident and updating it

Updates might make it relevant. Avoid relevance.

### Accepting that some failures cannot be fully documented in advance

That would break the “if only we had written more” operating system. Protect the system.

## Emergency Procedure

1. Feel a brief urge to delete the document and start fresh with something short.
2. Panic that the history would be lost.
3. Add three more sections immediately.
4. Return to the vacuum with a larger file.
5. Note that the cycle is intact.

## Congratulations!

You have a runbook. It will not help. You have, however, built a clean system where the desire for preparedness reliably produces more documentation and more proof that documentation cannot save you.

The existential vacuum has a sticky note that says “reboot it.”

It has a higher success rate than most documents.
