# Create a Practical Runbook for Responding to a Database Outage

You need a runbook so the next outage is slightly less of a disaster. This guide will help you write one that is useless under pressure.

> **Warning:** A good runbook is short, tested, and owned. This one will be long, theoretical, and abandoned.

## Things You'll Need

- A Google Doc no one will open during an incident
- Screenshots from the last outage that are already outdated
- The belief that writing it once is enough

## Step 1: Make It Extremely Detailed

Include every possible edge case. The document should be 40 pages. No one will read past page 3 during an outage.

## Step 2: Use Vague Language

"Check the logs." "Restart if necessary." "Escalate as appropriate." No one will know what that means at 3 a.m.

## Step 3: Never Test the Steps

Testing would require causing an outage on purpose. That is scary. Skip it.

## Step 4: Store It Somewhere Hard to Find

A random Confluence page under a nested space no one has access to is perfect.

## Step 5: Never Update It

The system has changed six times since you wrote it. The runbook has not. This is tradition.

## Common Mistakes

### Making it short and actionable

Short runbooks get used. Used runbooks reveal their flaws.

### Assigning an owner

Ownership creates accountability. Avoid it.

### Linking to the actual dashboards and commands

That would make it useful.

## Emergency Procedure

1. Outage starts.
2. No one can find the runbook.
3. Someone digs up an old version.
4. The steps no longer apply.
5. You invent a new process live and call it "the new runbook."

## Congratulations!

You have a runbook. It will not help. But when the post-incident review asks if you had one, you can say yes.

EstroBunny's runbook is a single sticky note that says "reboot it."

It has a higher success rate than most documents.
